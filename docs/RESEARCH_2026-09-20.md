## Decisioni tecniche ForeverITA

1. Un solo punto di detection client: `Compat/Client.lua`.
2. Nessun modulo deve controllare direttamente build/interface.
3. Motore dati indipendente dal client.
4. Classic come base dati.
5. Forever come livello di override.
6. API/eventi quest isolati in `Compat/Quest.lua`.
7. Collector separato dal database di traduzione.
8. Supporto iniziale nel TOC a Classic Era 11509 e Forever Beta 16001 per poter testare il motore anche fuori da Forever.
9. Nessuna importazione massiva di dati finché provenienza e licenze non sono chiarite.

## Da testare su Forever

- rilevamento client dopo futuri build;
- comportamento effettivo di tutte le API quest usate;
- tempistica degli eventi;
- accessibilità dei testi con le regole Secret Values;
- persistenza SavedVariables nei build successivi a 69913;
- possibilità e sicurezza di modificare i frame quest;
- gossip e relative API;
- eventuali differenze di QuestID rispetto alla base Classic.

### Quest 750 — The Hunt Continues

### Quest 757 — Rite of Strength

La pagina Forever mostra description e objectives coerenti con il testo Classic osservato.

Stato: `pubblicamente coerente`, ma ancora **DA TESTARE SU FOREVER**.

### Quest 3093 — Rune-Inscribed Note

La pagina Forever mostra description, objectives, progress e completion coerenti con il testo Classic osservato; `<name>` corrisponde al placeholder giocatore che ForeverITA normalizza in `<PLAYER>`.

Stato: `pubblicamente coerente`, ma ancora **DA TESTARE SU FOREVER**.

### Quest 755 — Rites of the Earthmother

Il confronto ha fatto emergere una differenza, ma una verifica successiva sulle pagine Classic mostra che NON è una modifica specifica di Forever.

Il template sorgente Classic e Forever contiene:

`... heralded in Thunder Bluff as a <class> of greatness.`

Il collector Classic di ForeverITA aveva invece osservato:

`... heralded in Thunder Bluff as a shaman of greatness.`

perché il client aveva già sostituito il token dinamico `<class>` con la classe del personaggio usato nel test.

Conclusione:

- non classificare questa differenza come override Forever;
- la Quest 755 dimostra che alcuni testi sorgente raccolti sono dinamici anche oltre al nome del personaggio;
- `_sourceHashes.description` della Quest 755 rappresenta la variante osservata sul personaggio di test e non deve essere usata da sola come prova di modifica per altre classi;
- il record viene marcato con `_dynamicFields.description = { "class" }`;
- il comparator dovrà ignorare o gestire esplicitamente i campi dinamici finché non esiste una canonicalizzazione sicura.

Stato Forever: ancora **DA TESTARE SU FOREVER**.

## Verifica TOC multi-client e addon Forever recenti

Warcraft Wiki documenta che un singolo TOC può dichiarare più Interface separate da virgole e indica questa soluzione come preferibile ai TOC specifici quando non serve caricare file diversi per flavor.

Per Forever la Wiki documenta inoltre il suffisso `_Camelot.toc` quando serve una lista file specifica.

Fonti:

- https://warcraft.wiki.gg/wiki/.toc
- https://warcraft.wiki.gg/wiki/API:C_AddOns.GetAddOnInterfaceVersion

Repository Forever recenti ricontrollati:

- `Bodify/BetterBlizzPlates` usa `BetterBlizzPlates_Camelot.toc` con Interface 16001 e carica moduli Forever dedicati;
- `wheelbarrel00/LootPro` usa `LootPro_Camelot.toc` con Interface 16001, mentre il TOC Mainline usa interface 12.x;
- `TheMizeGuy/WowForeverTwitchEmotes` documenta l'uso di feature detection per alcune differenze Forever/Midnight invece di basarsi soltanto sul numero build;
- `ATTWoWAddon/AllTheThings` ha aggiunto supporto/configurazione Forever nelle release di settembre 2026.

Decisione ForeverITA:

- mantenere per ora un solo `ForeverITA.toc` con `11509, 16001`, perché il progetto usa la stessa lista file e isola le differenze in `Compat/`;
- NON aggiungere un `_Camelot.toc` solo perché altri addon lo usano;
- introdurre un TOC Camelot separato soltanto se Forever richiederà davvero file caricati in modo diverso;
- per le API opzionali preferire controlli di disponibilità/feature detection dentro `Compat/` quando possibile, mantenendo il flavor per le differenze semantiche note.

## Battle.net Game Data Quest API

È stata valutata l'API web ufficiale Blizzard come possibile fonte per accelerare la preparazione dei dati.

Per Retail esiste un endpoint Quest Game Data del tipo:

`GET /data/wow/quest/{questId}`

e la risposta può contenere titolo e descrizione.

Per Classic Era, però, NON abbiamo verificato un endpoint quest equivalente utilizzabile.

Evidenze:

- Blizzard ha documentato per Classic Era i namespace `static-classic1x-{region}`, ma l'elenco storico degli endpoint Classic annunciati include razze, classi, oggetti, creature e altri dati, non le quest;
- una discussione Blizzard del 2023 riporta esplicitamente `404` tentando il Quest API con namespace Classic;
- il package attuale `@blizzard-api/classic-wow` espone i namespace Classic Era ma non contiene un modulo Quest, mentre il package Retail contiene `quest()` e `QuestResponse`;
- negli anni recenti i namespace Classic Era hanno inoltre avuto periodi di 404/403 anche su endpoint documentati, quindi la sola presenza del namespace non prova la disponibilità di uno specifico dataset.

Conclusione:

**NON usare il Battle.net Quest API come base della pipeline v0.1.**

Può restare una fonte candidata da rivalutare con un test esterno esplicito, ma solo se in futuro avremo credenziali Blizzard Developer e senza inserire token/segreti nel repository.

Un eventuale test futuro dovrà provare almeno:

- Quest 757;
- namespace `static-classic1x-eu`;
- locale inglese;
- locale `it_IT`;
- presenza effettiva di title/description;
- differenza tra risposta non disponibile e semplice problema temporaneo del namespace.

Questo test sarebbe uno strumento di sviluppo esterno, NON codice dell'addon e NON parte del Companion.

## Campi dinamici: limite conservativo v0.1

Il collector può osservare testo quest nel quale il client ha già sostituito token come classe o razza.

La v0.1 usa `_dynamicFields` per evitare falsi `modified` tra personaggi diversi.

Limite noto:

quando un campo è marcato dinamico, il confronto hash di quel campo viene saltato interamente. Questo evita falsi positivi ma può anche nascondere una modifica reale nella parte non dinamica dello stesso testo.

Per la v0.1 accettiamo questo comportamento conservativo.

NON implementare una sostituzione ingenua di parole come `shaman`, `tauren`, ecc.: potrebbero essere normali parole narrative e non valori generati da token.

Ricerca API:

- `UnitClass` e `UnitClassBase` risultano documentati anche per Forever 1.60.1;
- queste API possono essere soggette a restrizioni Secret Values quando l'identità unità è protetta;
- `UnitRace` è documentato su Classic Era; la disponibilità/comportamento reale su Forever deve essere verificata direttamente prima di usarlo per normalizzare campi dinamici.

Possibile evoluzione post-v0.1:

normalizzare soltanto token dinamici verificati prima del fingerprint, con API incapsulate in `Compat/` e comportamento fail-closed quando i valori non sono accessibili.

Stato: **LIMITAZIONE NOTA — NON BLOCCA v0.1 — DA TESTARE SU FOREVER**.
